# Report reminder emails (membership-management)

Handoff for the API side of **weekly report reminder emails**: once per church week (default
Saturday 08:00 in `CHURCH_TIMEZONE`) the worker writes one `small_group_report.reminder_due` outbox
row; its consumer emails each active leader / co-leader of an open group that hasn't submitted this
week's report (one email per person, drafts flagged) through the `report.reminder` template. The
preferences routes get a third switch, `reportReminder`. Outbox, claiming, sending and preferences
are Part 2's, reused as built.

- Rules and contracts: `../docs/specs/report-reminder-emails.md` (*rule N*), step 1 and
  *Contracts → membership-management*.
- Extends `docs/REPORT-SUBMITTED-EMAILS-API-HANDOFF.md` and `docs/ARCHITECTURE.md`,
  *Report conversations, Part 2*.
- auth-server (built in parallel; the template, strict `data` and path regex are fixed by the spec):
  `../auth-server/docs/REPORT-REMINDER-EMAILS-HANDOFF.md`. staff-app (after this repo):
  `../staff-app/docs/design/REPORT-REMINDER-EMAILS.md`.

Branch **`feature/report-reminder-emails`**. Each stage: `uv run ruff check src`, `uv run ty check`,
`uv run alembic check`.

## Decisions and deviations

- Migration `7e1a4c9b2d58` (revises `b453135219c0`) is hand-written, not autogenerated: no Postgres
  was reachable when it was built (Docker daemon down). It follows the conventions of the neighbouring
  migrations and matches the spec (`week_start DATE PK`, `triggered_at TIMESTAMPTZ NOT NULL DEFAULT
  now()`, no check constraint). `alembic check` and the `downgrade -1` / `upgrade head` round trip
  were NOT run: run them once the DB is up. `alembic upgrade b453135219c0:7e1a4c9b2d58 --sql` and the
  matching downgrade emit exactly the CREATE / DROP TABLE. (All since run against Postgres; see
  *Postgres checks* above.)
- `ReportReminderRun` lives in `data/small_groups/models/` (the spec doesn't say where).
- `NotificationSettings`: `church_timezone` is validated with `ZoneInfo` like `ApiSettings`; the
  reminder day must be 1-7; the reminder time must be a plain `HH:MM` (a UTC offset is rejected: it is
  local church time). The switch counts toward `any_emails_enabled` (embedded-worker gate in
  `api/main.py` and the standalone gate in `worker/__main__.py` already use it, so only comments and
  one log message changed) and toward the `INTERNAL_API_TOKEN` requirement.
- Trigger: `worker/reminder_trigger.py` (`trigger_report_reminder(session, now=None)`), called from
  `run_once` after `expire_overdue` and before the claim, inside its own try/except so a failure
  never stops the rest of the sweep. Day 7 = offset 0 (the Sunday that starts the same week). If the
  scheduled time is late enough for the 6 h window to cross midnight into the next church week (e.g.
  Saturday 21:00), the part after midnight belongs to the next week and does not fire: per the spec's
  math, only relevant to unusual schedules.
- Stage 2 on its own writes an event the worker would mark `dead` (unknown type): the consumer is
  registered in stage 3, same branch. Stage 2 adds a small `report_reminder_notifications.py` with
  only the constants so the commit is self-consistent.
- Consumer: `candidate_user_ids` ignores `possible_watchers` (leaders are found from the groups, not
  from permissions). `process_report_reminder` re-reads the no-meeting week, the groups and the drafts
  inside the fenced transaction, so a report submitted after the trigger is not reminded about. At
  most 50 groups per email (auth-server's maximum), sorted by name then id. Names are trimmed and cut
  to 200.
- `RunReport.reminder_triggered` is new and appears in the worker's log line.
- No test suite exists (as in Part 2, no `tests/`). Checks were scratch scripts, not committed:
  trigger (fake session): inside the window, outside it (07:59, 14:00, wrong day), idempotent second
  sweep, switch off, event fields (`aggregate_id`, payload, `expires_at` = scheduled_at + 6 h in UTC),
  day 7 = Sunday offset 0, day 1, UTC input; consumer (in-memory SQLite with the real queries,
  `create_deliveries` replaced by a recorder): church-wide no-meeting week, submitted skip (held and
  no-meeting, week edges), draft flag and latest draft (date desc, then id desc), closed groups,
  inactive / left / unlinked leaders, permission filter, candidate missing from the lookup, one email
  per person with several groups, rule 17 links, a submit after the trigger, `not_after`; preferences
  routes through `TestClient` (SQLite `notification_preferences`): default all on, `available`
  follows the kill switch, set one key without touching the others, `{email: {}}` 200, null and
  unknown keys 422, settable while the kill switch is off. Not covered, needs Postgres: the `ON
  CONFLICT` inserts, the migration, and a full `run_once` against the real DB.
- Production: turn on `REPORT_REMINDER_EMAILS_ENABLED` only once auth-server's `report.reminder`
  template is deployed.
- The handoff was written by the workspace session from the subagent's returned text, because
  Claude Code refused the subagent's new `.md` as a "report file".
