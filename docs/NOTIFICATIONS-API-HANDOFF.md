# Notifications, Part 1: in-app list (membership-management)

Handoff for the API side of the **in-app notification list**: every notification the three
consumers already email (conversation comments, submitted reports, weekly report reminders) also
becomes one `user_notifications` row per recipient, listed by `GET /me/notifications`, counted by
`GET /me/notifications/unread-count`, marked read by two POST routes, auto-read by opening a thread
(rule 13) or submitting a report (rule 14), and purged after 90 days. Outbox, worker, claiming,
`notifications/` and preferences are the email work's, reused as built. **Nothing from Part 2
(push).**

- Rules and contracts: `../docs/specs/notifications.md` (*rule N*), Part 1 step 1 and *Contracts
  (Part 1: in-app) → membership-management*.
- Extends `docs/REPORT-CONVERSATIONS-EMAIL-API-HANDOFF.md`, `docs/REPORT-SUBMITTED-EMAILS-API-HANDOFF.md`,
  `docs/REPORT-REMINDER-EMAILS-API-HANDOFF.md` and `docs/ARCHITECTURE.md`, *Report conversations, Part 2*.
- staff-app (after this repo is merged): `../staff-app/docs/design/NOTIFICATIONS.md`.

Branch **`feature/notifications`**. Each stage: `uv run ruff check .`, `uv run ruff format --check .`,
`uv run ty check`, `uv run python -m unittest discover -s tests`, `uv run alembic check`.

   (`id` bigint identity, `user_id`, `source_event_id`, `category`, `template`, `data` jsonb, `path`,
   `subject_key`, `small_group_ids` int[] null, `created_at`, `read_at`), unique
   `(source_event_id, user_id)`, indexes `(user_id, id desc)`, partial `(user_id) where read_at is

   (`IN_APP_NOTIFICATIONS_ENABLED`, default false).

4. **Read side effects.** Rule 13 in `mark_read` and `mark_all_read`; rule 14 in the submit

## Decisions and deviations

- Migration `ea20b44459b8` (revises `7e1a4c9b2d58`) is autogenerated and reviewed; `alembic check`,
  `downgrade -1` and `upgrade head` all run clean against the local Postgres. The `(user_id, id desc)`
  index really is descending in the database.
- Gating (rule 3): entries are written only when the kind's flag AND `IN_APP_NOTIFICATIONS_ENABLED` are
  on, checked inside each consumer (an event written while the kind was on but processed after it was
  turned off writes no entry, though its emails still go). The worker gate `any_emails_enabled` needed
  no change: a kind on with in-app on already keeps the worker running; in-app on with every kind off
  writes nothing and runs no worker. The flag needs no `INTERNAL_API_TOKEN`.
- The reminder entry's `small_group_ids` holds **every** group the person owes (sorted by id), not only
  the at most 50 the email lists, so rule 14 clears it only when all of them have submitted.
- Rule 7: no backend change. The Watching switches' "disabled when every email switch is off" logic is
  staff-app's (it reads `available`); staff-app must keep them enabled while `unread-count` says
  `enabled: true`. Unwatching affects **future** entries (the consumers' opt-out rule); entries already
  written are not deleted.
- Rule 13: `mark_read` and `mark_all_read` touch entries only while the in-app flag is on (in the same
  transaction; read-all through a second data-modifying CTE in the existing statement, so it stays one
  round trip). Entries with an unknown thread id are untouched by read-all.
- Rule 14: `_on_report_submitted` (both submit paths: create with `status = submitted`, and
  `POST /small-group-reports/{id}/submit`) runs `clear_reminder_entries` before the submitted event,
  **independently of `REPORT_SUBMITTED_EMAILS_ENABLED`** (it needs only the in-app flag). The church week
  is `church_sunday(report.meeting_date)`; "submitted" is the reminder's own test (status `submitted`,
  `meeting_date` in the week, held or not). A **church-wide no meeting** creates its reports outside
  this path, so a reminder entry is not auto-cleared by one (spec rule 14 says "when a report is
  submitted"; the reminder isn't sent for such a week anyway). Not done: say so if it should be.
- `POST /me/notifications/{id}/read` and `read-all` use one UPDATE (idempotent, `read_at` never moves
  once set). Rate limits: the router default on the list and the count; `120/minute` on
  `{id}/read`, `30/minute` on `read-all`.
- Purge: `purge_entries` (`worker/maintenance.py`) deletes by `created_at` older than 90 days in
  batches of 1000 (at most 10 per run), oldest id first; reported as `purged["notifications"]`. It
  runs every sweep whatever the flag says. No extra index on `created_at`: ids follow it.
- No tests directory pattern exists for the API (only `tests/test_check_hook.py`), so none were added.
  Checks were scratch scripts (not committed) against the local Postgres with `TestClient` and a claims
  override: flag off (count `{enabled:false,unread:0}`, the others 404 `notifications_disabled`), paging
  (`limit` 1-50 else 422, `nextBefore`, null on the last page), read idempotent, another user's id and a
  missing id 404, read-all only the caller's, `create_entries` idempotent per `(event, user)`, rule 13
  (`mark_read`, `mark_all_read`), rule 14 (all groups submitted / one still owing / another week), purge
  boundary (91 days gone, 89 kept).
- No seeder added (optional in the brief): a seeded entry would be fake output of events that never ran.
  Trigger real ones locally by turning on a kind flag plus the in-app flag.
