# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

Early-stage: no tests or CI yet, but real code exists beyond the placeholder entry point. Treat architecture notes below as provisional — update this file as real structure gets added.

This is a single microservice for church membership management (membership applications, members, small groups and small-group reports), sitting alongside an existing church web application. See `docs/ARCHITECTURE.md` for this service's architecture and `docs/ROADMAP.md` for near-term plan — don't inline that detail here; this file should stay short since it's loaded into every agent session.

## Commands

This project uses [uv](https://docs.astral.sh/uv/) with the `uv_build` backend (Python >=3.14, pinned via `.python-version`).

- Sync dependencies / create the venv: `uv sync --all-packages` (plain `uv sync` only syncs the root
  project's own dependencies, not workspace members like `src/membership_management/api` — it will
  silently *uninstall* `fastapi`/`pyjwt`/etc. if they were previously synced in, since they're not a
  root-level dependency)
- Run the console script (currently just the placeholder `main()`): `uv run membership-management`
- Run the actual CLI logic (lists recent membership applications): `uv run python -m membership_management.cli.main`
- Run the FastAPI development server (use for day-to-day local coding — auto-reloads, binds 127.0.0.1, ignores `PORT`/`WORKERS`/keep-alive/graceful-shutdown/`limit_concurrency`/`backlog` from `.env`, since it never calls `run.py`'s `uvicorn.run()`): `uv run --package membership-management-api fastapi dev src\membership_management\api\main.py`
- Run the FastAPI production-style server (use whenever a change touches one of the uvicorn-level settings above and you need to see it actually take effect locally, not just for staging/production/Docker — no auto-reload, binds 0.0.0.0, reads `PORT`, `WORKERS`, keep-alive/graceful-shutdown timeouts, and `limit_concurrency`/`backlog` from `.env`): `uv run --package membership-management-api python -m membership_management.api.run` (invokes `uvicorn` directly rather than `fastapi run`, since `fastapi run` can't set those uvicorn-level flags)
- Build the package: `uv build`
- Lint: `uv run ruff check .` (config in `ruff.toml`); pre-commit hooks are set up via `.pre-commit-config.yaml`
- Type-check: `uv run ty check` ([`ty`](https://github.com/astral-sh/ty), Astral's type checker — no separate config file yet)
- Migrations (members DB only): `uv run alembic revision --autogenerate -m "..."`, then **review the generated file** (autogenerate drops any table whose model isn't imported via `data/models.py`) before `uv run alembic upgrade head`. `uv run alembic upgrade head --sql` previews the SQL without touching the DB; `uv run alembic check` fails if models changed without a migration; check `downgrade -1` + `upgrade head` round-trips. Generated files are ruff-fixed and formatted by post-write hooks in `alembic.ini`. Deployments run `python -m membership_management.data.migrate` (no `alembic.ini` in the image) as a one-off task before the service update, never on app startup. Locally the DB URL must use `127.0.0.1`, not `localhost` (`::1` hangs against Docker Desktop's Postgres).

- Seed the members DB with deterministic Managua demo data: `uv run python -m membership_management.data.seed` (refuses if any table has rows; `--reset` truncates every members-DB table first; refuses in production). New tables: add a `seed_<domain>(ctx)` module under `data/seed/` and register it in `runner.SEEDERS`.

Run commands from the repository root so settings load the root `.env`. `.env` is skipped when `ENVIRONMENT` is `staging`/`production` in the real environment (`env_file.py`), so deployments use real env vars only.

## Architecture

- Packaging: `pyproject.toml` defines a console script `membership-management` that maps to `membership_management:main` (still the placeholder — not yet wired to real logic). `src/membership_management/api` is a separate `uv` workspace member with its own `pyproject.toml`.
- `src/membership_management/cli/main.py` — queries membership applications generated in the last 30 days from the assimilation DB and prints them.
- `src/membership_management/api/main.py` — FastAPI app: `GET /applications/recents` returns recent applications via the same service layer as the CLI; `POST /applications/approve` and `/applications/reject` are placeholders that don't yet persist status changes. `GET /health` pings each DB (`assimilation`, `members`) separately with `SELECT 1` and reports, per DB, its status and this process's connection-pool stats (`size`/`checked_out`/`overflow`); it returns 503 with the same body if any DB is unreachable, so the body names which one. `GET /health/live` is the liveness check for container healthchecks (compose, ECS): an `async` route that touches no DB, so a dependency outage doesn't get tasks restarted in a loop. A `lifespan` hook sets anyio's default thread-pool limiter from `ApiSettings.thread_pool_size` on startup (bounds concurrent sync `def` routes/dependencies) and calls `engine.dispose()` on shutdown.
- `src/membership_management/api/config.py` — `ApiSettings`: CORS origins, `port`, `workers`, request/keep-alive/graceful-shutdown timeouts, the default rate limit, uvicorn's `limit_concurrency`/`backlog`, and `thread_pool_size` (see `.env.example`). `workers > 1` multiplies the DB pool ceiling (each worker is a separate process/engine/pool) and silently breaks the in-memory rate limiter's per-route counts — see `rate_limit.py`. `thread_pool_size` bounds concurrent sync (`def`) route handlers separately from the DB pool — if it's smaller than a DB's `db_pool_size + db_max_overflow`, it becomes the binding concurrency limit instead of that DB's pool. The API's `lifespan` disposes both DB engines on shutdown.
- `src/membership_management/api/middleware.py` — `RequestLoggingMiddleware` and `RequestTimeoutMiddleware` (returns 504 past `REQUEST_TIMEOUT_SECONDS`).
- `src/membership_management/api/rate_limit.py` — per-user rate limiting built directly on the `limits` library (moving-window strategy), not a slowapi middleware. `rate_limit(spec, scope=...)` returns a FastAPI dependency that runs after JWT verification and keys on the verified `sub`; `default_user_rate_limit` (from `ApiSettings.default_rate_limit`) is attached to every router, and stricter per-route limits (approve/reject) are added as route-level `dependencies=[...]`. Over-limit requests get 429 with `Retry-After` and `RateLimit-*` headers. Storage comes from `ApiSettings.rate_limit_storage_uri` (`memory://` by default, so counters aren't shared across `ApiSettings.workers` or replicas — a "60/minute" limit becomes "60 x (workers x replicas) per minute" if either is raised; use a shared Redis URI to fix that). Deliberately no per-IP limiting of anonymous traffic: that belongs at the edge (Cloudflare/WAF), and needs revisiting before this API is exposed publicly.
- `src/membership_management/api/run.py` — production-style entry point (`python -m membership_management.api.run`, no auto-reload): calls `uvicorn.run()` directly so `port`, `workers`, keep-alive/graceful-shutdown timeouts, and `limit_concurrency`/`backlog` from `ApiSettings` take effect. Use `fastapi dev` instead for local coding.
- `src/membership_management/data/query_helpers.py` — `first_as`/`all_as` map SQLAlchemy `Select` rows onto a dataclass or `NamedTuple` by column name.
- `src/membership_management/data/base_db_settings.py` — `BaseDbSettings`: loaded from env vars and, outside staging/production, the root `.env` (see `env_file.py`). `ENVIRONMENT` is required; `DEBUG` defaults to `False` and is rejected in production; both are pinned via `validation_alias` so subclass prefixes don't apply to them. `PooledDbSettings(BaseDbSettings)` adds `database_url` plus the connect/query/pool timeouts and pool sizing (`db_pool_size`, `db_max_overflow`, `db_pool_pre_ping`, `db_pool_use_lifo`, ...); each DB subclasses it with its own `env_prefix` (`ASSIMILATION_`, `MEMBERS_`), so env vars are `ASSIMILATION_DB_POOL_SIZE`, `MEMBERS_DB_POOL_SIZE`, etc. and each DB is tuned independently.
- `src/membership_management/data/pooled_engine.py` — `create_pooled_engine(settings, connect_args=...)`: the shared QueuePool engine factory (`pool_reset_on_return="rollback"` is fixed, not configurable). Each DB's `database.py` passes only its driver-specific `connect_args`: pyodbc's `timeout` plus a `connect` event setting the query timeout for SQL Server; psycopg's `connect_timeout` plus server-side `statement_timeout`/`idle_in_transaction_session_timeout` for Postgres. Alembic's `env.py` builds its own NullPool engine with no statement timeout, and in its transaction takes `pg_advisory_xact_lock` (a concurrent run waits, then applies nothing) before `SET LOCAL lock_timeout` (`MEMBERS_MIGRATION_LOCK_TIMEOUT_SECONDS`; after the advisory lock, since `lock_timeout` applies to it too).
- Members DB (Postgres via psycopg 3; this service's own DB, separate from auth-server's): `data/config.py` (`MEMBERS_DATABASE_URL`), `data/database.py` (`engine`, `MembershipSessionLocal`, `MemberManagementBase` with a constraint naming convention so migrations get deterministic names). Models live per domain in `data/<domain>/models/` (`members`, `small_groups`), each exported from its `models/__init__.py`, and every domain package must be imported in `data/models.py`, the registry that both Alembic's `env.py` and `api/main.py` import (so cross-domain `relationship()`s resolve at runtime). Alembic (`data/migrations/`, config in root `alembic.ini`, `script_location` is the package resource `membership_management.data:migrations`) owns this whole DB and only this DB — never the assimilation DB. `small_group_members` keeps history: one row per membership period (`joined_at`/`left_at`) and role (`member`/`leader`/`co_leader`); partial unique indexes enforce one active row per member per group and one active leader per group; groups are closed (`closed_at`), not deleted. `role` is VARCHAR + CHECK, so adding a role needs a hand-written migration (autogenerate doesn't detect it). `GET /small-groups` includes each group's active leader (`leaderMemberId`/`leaderName`, null if none or closed); `PUT /small-groups/{id}/leader` demotes the current leader to co-leader and promotes (or adds) the target in one transaction, and closed groups reject every edit with 409. `members.sex` is VARCHAR + CHECK (`male`/`female`, nullable), so a new value needs a hand-written migration too. `members.user_id` is a cross-service reference to an auth-server user with no FK, set only through `PUT/DELETE /members/{id}/user` (`members: link`) and the internal `POST /internal/member-links/accepted-invite` (shared `INTERNAL_API_TOKEN` in `X-Internal-Token`, not a JWT; disabled locally when unset, required in staging/production). The current member is resolved from the JWT `sub` through `members.user_id` (`get_current_member` in `api/current_member.py`, `GET /me`); the JWT carries no member id. **Authorization checks permissions, never role names**: the JWT's `perms` claim (computed by auth-server from its `statements.ts`; missing means none) via `require_permission(resource, *actions)` / `has_permission` in `api/jwt_auth.py`, plus record scopes in `api/access.py` (`SmallGroupScopeDep`: `smallGroups: all` or the groups the caller's member leads / co-led when closed; `MemberScopeDep`: `members: all` or members active in an open group of that scope; 404 outside the scope, 403 without the permission). Every route names its permission except `GET /me`, `/health` and `/internal/*`; `PATCH /me/member` (name, phone, address, birthDate, sex of the caller's own linked member; no email, no scope) needs `ownProfile: update`, and `GET /members/{id}` always lets a caller read their own member (My profile); role × route table in `docs/ARCHITECTURE.md`, *Permissions*. A new role needs no change here. Small group reports (`api/routers/small_group_reports.py`, services in `data/small_groups/services.py`) reuse the small group scope; attendance observations need `smallGroupReports: viewObservations` or being the submitter (`docs/ARCHITECTURE.md`, *Small group reports*). A "no meeting" is a report with `held = false` (no attendance, optional reason); queries that mean "a meeting with attendance" must filter `held` (`docs/ARCHITECTURE.md`). Date-only "today" (joins, leaves, close) is `church_today()` (`api/church_time.py`, `CHURCH_TIMEZONE`, default `America/Managua`), never UTC.
- Guests (`docs/ARCHITECTURE.md`, *Guests and guest groups*, `docs/GUEST-SMALL-GROUPS-API-HANDOFF.md`): people who aren't members, in `data/guests/` (own table, never in `members`), taking part in groups whose `audience` is `guests` (fixed at creation; the database refuses a guest in a member group or as leader). `GUEST_GROUPS_ENABLED` (off by default, `features.guestGroups` in `GET /me`) only gates *creating* a guest group or a guest (409). Inserts of `SmallGroupMember` go through `SmallGroupMember.for_group`; search uses the `guest_search_text` wrapper and its trigram indexes, not `unaccent()` directly; attendance, roster and conversation rows hold a `member_id` or a `guest_id` (`PersonKey`).
- Report items and tags (`docs/ARCHITECTURE.md`, *Items and tags*, `docs/REPORT-TAGS-API-HANDOFF.md`): a held report's prayer, praise and follow-up are rows in `small_group_report_items` (+ `…_item_people`), written from the body's required `sections` (segments) in `data/small_groups/report_items.py`; the text stores tags as `@{member:id}` / `@{guest:id}` tokens, never names. The old `groupPrayerRequest`-style fields no longer exist. `GET /small-groups/{id}/tag-search` feeds the `@` picker.
- Person timeline (`docs/ARCHITECTURE.md`, *Person timeline*): `GET /members/{id}/timeline` and `GET /guests/{id}/timeline` (`api/person_timeline.py`, `data/small_groups/timeline_services.py`) list the held reports where someone is on the attendance list or tagged in an item. Attendance, notes and follow-up items show only for groups in the caller's observation audience (`conversation_group_ids`), prayer and praise items for any group; range errors are 422 with `range`.
- Report conversations (Part 1, in-app only; `docs/ARCHITECTURE.md`, *Report conversations*): `api/routers/report_conversations.py`, services in `data/small_groups/conversation_services.py`. A thread per attendance row or per report section (`prayer`/`praise`/`followUp`, exactly one anchor; `docs/PRAYER-FOLLOW-UP-API-HANDOFF.md`), readable by whoever may see the report's observations (`conversation_access` / `conversation_group_ids` in `api/access.py`, no new permission); every write needs a linked member (409). Don't add email or outbox code here before Part 2.
- `src/membership_management/data/assimilation/` — SQLAlchemy data layer for the existing SQL Server DB (the "assimilation" system):
  - `config.py` — `Settings(PooledDbSettings)` with `env_prefix="ASSIMILATION_"`; requires `ASSIMILATION_DATABASE_URL`.
  - `database.py` — SQLAlchemy `engine` (from `create_pooled_engine`), `SessionLocal`, declarative `Base`.
  - `models/membership_applications/` — the `MembershipApplication` model (maps to existing `MemberShipApplications` table), `queries.py` (typed `Select` builders), `services.py` (business/query-window logic, e.g. the 30-day recent-applications window), and `results.py` (`NamedTuple` result types).
  - `models/person/person.py` — the `Person` model (maps to the existing `Persona` table), joined against membership applications.
- The FastAPI routes call the `services.py` functions directly (no repository abstraction layer) — see `docs/ROADMAP.md` for how that decision was reached and what's still open.
